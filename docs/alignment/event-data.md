# Shared event data: alignment analysis

This report compares the website's event data (`src/content/meetups/*.json`, schema in `src/content.config.ts`) with the equivalent facts held in the slides repository (content pack, `AGENTS.md`, and `slides.jsx`). It covers the November 2026 event, a field-by-field map of the website schema against the slides repo, and a recommendation for a single source of truth.

## Options for a single source of truth

| Option                                                                  | Effort                                                                                                                                                                                                                                                          | Failure modes                                                                                                                                                                                                                                                                                                                                                                | Pages CMS fit                                                                                                                                                                                |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Website JSON as master; slides repo reads from it                       | Medium. Slides repo adds a build step (currently none, per AGENTS.md:45-47, "no build step") to fetch and parse the website's JSON, or a person copies values across by hand at pack-writing time.                                                              | The schema still cannot hold co-speakers, doors time, floor, or per-talk agenda slots, so slides-only facts stay hand-maintained regardless. Pages CMS edits made close to the event (for example a speaker swap) would need a slides repo rebuild step that does not exist today to take effect on slides.                                                                  | Good. Pages CMS already edits the JSON, so editors keep today's workflow; no new editing surface needed.                                                                                     |
| Slides content pack as master; website JSON generated or copied from it | Medium to high. Needs a script to lift the subset of content pack facts the schema can hold into a conforming JSON file, since the content pack carries narrative detail (bios, access logistics, design notes) the schema does not model.                      | The content pack is written and revised by hand across an event's run-up (content-pack.md:5 describes it as the single input for the slide-writing process), so it is not yet in a stable, parseable shape; a generator would break on every pack restructure. Also moves editorial control away from Pages CMS, which is the website's existing non-technical editing path. | Poor. Would sideline Pages CMS for the fields it currently owns.                                                                                                                             |
| Shared data file or package both repos consume                          | High upfront, lower upkeep after. A new JSON or TypeScript module, versioned and published (or vendored) into both repos, holding the fields both repos need (and only those); each repo keeps its own schema-specific or presentation-specific extras locally. | Two consumers drifting in which version of the shared file they pin is a new failure mode; needs a release or sync step on every edit. Also the biggest change to make, for a two-repo, community-run project.                                                                                                                                                               | Fair. Pages CMS still edits the website's copy of the shared fields; the generated or synced file becomes the thing that needs a validation check (see below), not a second editing surface. |

### Recommendation

Make the website JSON the master for every fact both repos need (title, date, start/end time, venue, speakers, roles, talk titles, sponsors, organisers), since Pages CMS already edits it and it is the only one of the three sources with a defined, checkable shape (the Zod schema in `src/content.config.ts`). Extend the schema in a follow-on piece of work to hold doors time and per-talk agenda slots, and to allow more than one speaker per talk; until that schema change lands, those three facts stay hand-maintained in the slides repo as they are today.

**Sync mechanism:** add a small script to the slides repo (run manually when building a content pack, not on every slides.jsx edit) that fetches the current event's JSON file from the website repo's `main` branch and prints a diff against the facts already written into the content pack's Title, Lineup, Agenda, Host and Welcome sections. This keeps the content pack as the place a human resolves wording, while surfacing fact drift (like the role-text bundling and the "Albany" against "Albany Growth" case above) before the pack is finalised.

**Validation check:** add a CI check to the website repo (an ESLint rule or small Node script run in the existing `lint` step) that fails if any `talks[].speaker.role` or `organizers[].role` string contains the word "at", or any other separator pattern that signals a bundled title-and-employer string. This would have caught the Talk 1 and Talk 2 drift rows above at the point the JSON was written, rather than at a cross-repo review.

## Recommendations summary

- Fix the Talk 1 and Talk 2 role strings, and the "Albany Growth" against "Albany" organiser mismatch, directly in `meetup-nov-26.json`. QUICK WIN.
- Adopt the website JSON as the single source of truth for the fields it already holds, per the recommendation above. FOLLOW-ON.
- Add a sync script to the slides repo that diffs the content pack against the website JSON when a content pack is being written. FOLLOW-ON.
- Add a CI validation check in the website repo for bundled title-and-employer role strings. FOLLOW-ON.
- Extend the `meetups` schema to support co-speakers, a doors time, and per-talk agenda slots, so the three facts marked "absent from schema" above can move onto the website JSON too. FOLLOW-ON.
